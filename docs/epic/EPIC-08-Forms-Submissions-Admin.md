# EPIC-08 — Forms & Submissions (Landing · Certificate · Admin)

> **Feature**: three public intake forms (Advanced Course Interest · Free Course Waitlist · Instructor Application) feeding a single admin surface for viewing, visualising and evaluating submissions.
>
> **Status**: implementation plan · **v1.1** — revised against the source PDF *and* the running database schema; every change is listed in §0.4
> **Stack**: NestJS + PostgreSQL + TypeORM (BE) · Next.js + Zustand (+ MUI where already adopted) (FE)
> **Surfaces**: Landing page (`/`) · Certificate screen `STU_CER_10` · Admin screen `ADM_FRM_20` (new)
>
> **V1 scope**: the three forms, the admin workflow and CSV export. Charts follow the data (§11, §13).

## 0. Scope
### 0.1 Forms in scope

| Code | Form | Source questions | Surface | Entry point |
|---|---|---|---|---|
| `free_course_waitlist` | Đăng ký nhận thông báo khoá học miễn phí | 5 | Landing page | Inline band after the course grid |
| `instructor_application` | Đăng ký trở thành giảng viên | 15 (3 groups) | Landing page | 4-step wizard in the `#giang-day` section |

### 0.2 Out of scope (V1)

- Payment / tuition collection for advanced courses
- Auto-assignment of students into cohorts by algorithm (V1 gives the operator a roster view + manual grouping)
- AI clustering of free-text answers (V1 = manual read; tagging moved to V1.1)
- Marketing automation / drip campaigns
- **Every chart except the KPI strip** — deferred to V1.1 and gated on real data (§11, §13). A heatmap cannot be validated against zero submissions.

### 0.3 Design principle that drives everything

> **Aggregation is a schema decision, not a dashboard decision.**
> Every enumerable answer is stored as a **stable option code**, never as free text. All charts in `ADM_FRM_20` are then plain `GROUP BY` queries. Any question stored as a raw string becomes permanently un-chartable.

### 1.1 Platform facts this plan must respect

Checked against the repository, not assumed. Getting these wrong costs a failed migration or a rewritten module.

| Fact | Consequence for this epic |
|---|---|
| `user.id` is **`integer`**; `course.id` is **`uuid`** | `user_id integer REFERENCES "user"(id)`, `selected_course_id uuid REFERENCES "course"(id)` |
| Table names are **singular** (`user`, `course`, `master_data_code`, `instructor_expertise`) | Use `form_submission`, `form_answer`, … not the plural names in the first draft |
| uuid default is **`uuid_generate_v4()`** (uuid-ossp), not `gen_random_uuid()` | Match it; the pgcrypto extension is not installed |
| Timestamps are **`timestamptz`** since `1787200000000` | New tables are timestamptz from the start |
| Master data lives in `master_data_group` (`group_key`) / `master_data_code` (`code`, `group_id`, `name_translations` jsonb with a `vi` CHECK) | Reuse it exactly; no new options table |
| Groups **already seeded**: `expertise_area`, `career_interest`, `education_stage`, `learning_goal`, `course_category`, `course_level`, `course_group`, `course_status`, `lecture_type` | `learning_goal` collides head-on with this plan's draft; see §2.1 |
| `master_data_code` has **no unique index on `(group_id, code)`** | The seed must be idempotent by `(group_id, code)` lookup, and should add that unique index while it is there |
| There is **no global `APP_GUARD`** — a controller without `@UseGuards` is public | `/public/forms/*` needs no new "public" decorator, but it also gets **no `request.user`**, so prefill needs its own authenticated endpoint (§4) |
| `RateLimitGuard` + `@RateLimit(limit, windowMs, by)` already exist (`by`: `'ip'`, `'caller'`, `{ body }`, `{ param }`), send `Retry-After`, honour `RATE_LIMIT_IP_MULTIPLIER`, and keep counters **in process memory** | §8 reuses them; no `FORM_RATE_LIMIT_*` env vars |
| Permissions are rows: `module` + `permission` + `role_permission`, seeded by migration `1787700000003` | `forms:*` needs its own migration inserting the module, the four permissions and the Admin grants |
| `CLAUDE.md`: entities are generated (`npm run generate:resource:relational`), never hand-written | P1 runs the generator first, then edits the generated migration |

## 2. Data model
### 2.1 Where options live

All enumerable choices are **`master_data_group` / `master_data_code` rows**, reusing the EPIC-06 i18n pattern (`name_translations` JSONB, `vi` default, `en` supported, `COALESCE` fallback). This is deliberate:

- free vi/en translation for every option (already built)
- stable `code` values survive label edits — the property every chart depends on
- one place to add "Khác" follow-ups

**Two rules, both learned the hard way**

1. **Reuse before create.** Three groups in this database already describe "what field is this person in" (`expertise_area`, `career_interest`) and "what do you want out of it" (`learning_goal`). A fourth version of the same idea cannot be joined to the first three.
2. **Every group this epic creates is prefixed `form_`.** The first draft proposed a group literally named `learning_goal`, which already exists with different codes (`university_career`, `job_transition`, `deeper_understanding`, `core_skills`) and live onboarding rows pointing at it. The prefix makes that class of collision impossible.

**Groups**

| Purpose | Group | Action | Codes |
|---|---|---|---|
| Profession / field (A, B, C) | **`expertise_area`** | ♻️ **extend** | has `data_analytics`, `supply_chain`, `software_dev`, `digital_marketing`, `finance`, `human_resources`, `design`, `career_coaching` → **add** `business_analysis`, `software_testing_qa`, `project_management`, `product_management`, `ui_ux`, `other`, `undecided` |
| Current situation (A, B) | **`education_stage`** | ♻️ **extend** | has `middle_school`, `high_school`, `university`, `graduated`, `working` → **add** `career_switch`, `other` |
| Current level in the field (A) | `form_current_level` | new | `dna_intro_completed`, `has_basics`, `self_taught`, `project_experience`, `working_in_field` |
| Goal after the course (A) | `form_learning_goal` ⚠️ **prefixed** | new | `upskill`, `apply_to_current_job`, `real_project`, `portfolio`, `internship_fresher`, `career_switch`, `promotion`, `other` |
| Availability (A) | `form_session_slot` | new · **merged, multi-select** (D10) | `weekday_evening`, `sat_morning`, `sat_afternoon`, `sun_morning`, `sun_afternoon`, `other` |
| Preferred hour band (A) | `form_time_band` | new · optional refinement | `slot_18_20`, `slot_19_21`, `slot_20_22`, `flexible` |
| Weekly study hours (A) | `form_weekly_hours` | new | `lt_3`, `3_5`, `5_8`, `gt_8` |
| Referral source (B) | `form_referral_source` | new | `facebook`, `tiktok`, `youtube`, `friend_referral`, `other` |
| Skills to improve (A) | `form_skill` | new · **parent-linked** to the profession question (§3.2) | BA list from the PDF, verbatim, + `other` |
| Contribution mode (C) | `form_contribution_mode` | new | `teach`, `build_content`, `design_exercise`, `share_case_study`, `review_content`, `mentor_career_talk`, `undecided` |

| Monthly capacity (C) | `form_monthly_capacity` | new | `lt_5`, `5_10`, `10_20`, `gt_20`, `discuss` |
| Has taught before (C) | — | no group | a `single_select` with two literal codes `yes` / `no` |

> `undecided` on the profession group exists because Form B offers "Chưa xác định". It is a legitimate answer and a **non-signal**: §6.2 and §6.5 exclude it from demand.

### 2.2 Form definition tables

```sql
CREATE TABLE form_definition (
  id                       uuid PRIMARY KEY DEFAULT uuid_generate_v4(),
  code                     varchar(64)  NOT NULL UNIQUE,
  name_translations        jsonb        NOT NULL,
  description_translations jsonb,
  version                  int          NOT NULL DEFAULT 1,
  is_active                boolean      NOT NULL DEFAULT true,
  created_at               timestamptz  NOT NULL DEFAULT now(),
  updated_at               timestamptz  NOT NULL DEFAULT now()
);

CREATE TABLE form_question (
  id                     uuid PRIMARY KEY DEFAULT uuid_generate_v4(),
  form_definition_id     uuid NOT NULL REFERENCES form_definition(id) ON DELETE CASCADE,
  code                   varchar(64) NOT NULL,          -- stable analytics key
  section_code           varchar(64) NOT NULL,          -- student_info | learning_needs | schedule | about_you | consent
  question_type          varchar(32) NOT NULL CHECK (question_type IN
                           ('short_text','long_text','email','phone','url',
                            'single_select','multi_select','consent')),
  master_data_group_key  varchar(64),                   -- set when options come from master data
  is_required            boolean NOT NULL DEFAULT false,
  display_order          int     NOT NULL DEFAULT 0,
  label_translations     jsonb   NOT NULL,
  placeholder_translations jsonb,
  helper_translations    jsonb,
  min_length             int,
  max_length             int,                           -- enforced server-side; default FORM_LONG_TEXT_MAX_DEFAULT
  allow_other            boolean NOT NULL DEFAULT false,-- renders the "Khác" free-text box
  consent_code           varchar(64),                   -- consent questions only, e.g. 'zoom_format' | 'contact'
  parent_question_id     uuid REFERENCES form_question(id) ON DELETE CASCADE,
  parent_option_code     varchar(64),                   -- render only when the parent answer includes this
  created_at             timestamptz NOT NULL DEFAULT now(),
  updated_at             timestamptz NOT NULL DEFAULT now(),
  UNIQUE (form_definition_id, code)
);

-- C3. A question shows a SUBSET of its group, in its own order.
-- Form A offers 6 professions (the ones with a course); Form B offers 11.
-- `master_data_group_key` alone cannot express that, and without this table the
-- FE ends up hard-coding the subsets — losing the whole point of a data-driven form.
CREATE TABLE form_question_option (
  id            uuid PRIMARY KEY DEFAULT uuid_generate_v4(),
  question_id   uuid NOT NULL REFERENCES form_question(id) ON DELETE CASCADE,
  option_code   varchar(64) NOT NULL,
  display_order int NOT NULL DEFAULT 0,
  UNIQUE (question_id, option_code)
);
```

An empty allowlist means "every active code in the group" — so a question that really does offer the whole group needs no rows.

`parent_question_id` + `parent_option_code` is what makes **Form A's skill checklist adapt to the chosen profession**, and it is still fully aggregatable: each skill question has its own `id`, so "which skill is most requested" is a `GROUP BY question_id`.

### 2.3 Submission tables

```sql
CREATE TABLE form_submission (
  id                  uuid PRIMARY KEY DEFAULT uuid_generate_v4(),
  form_definition_id  uuid NOT NULL REFERENCES form_definition(id),
  form_version        int  NOT NULL,
  user_id             integer REFERENCES "user"(id) ON DELETE SET NULL,   -- integer: see §1.1
  full_name           varchar(160) NOT NULL,
  email               varchar(255) NOT NULL,
  email_normalized    varchar(255) NOT NULL,      -- lower(trim(email)); dedupe + join key
  phone               varchar(32),
  -- C4. ONLY set when the form's profession question is single_select (Forms A and C).
  -- Form B is multi-select: its demand is read from form_answer_option, never from here.
  primary_field_code  varchar(64),
  selected_course_id  uuid REFERENCES "course"(id) ON DELETE SET NULL,
  status              varchar(24) NOT NULL DEFAULT 'new' CHECK (status IN
                        ('new','reviewing','contacted','grouped','approved','rejected','archived')),
  assigned_to_user_id integer REFERENCES "user"(id) ON DELETE SET NULL,
  internal_notes      text,
  -- C6. Append-only: a re-submission inserts a new row and flips the old one.
  is_latest           boolean NOT NULL DEFAULT true,
  superseded_by_id    uuid REFERENCES form_submission(id) ON DELETE SET NULL,
  source              varchar(24) NOT NULL DEFAULT 'landing'
                        CHECK (source IN ('landing','certificate','catalog','other')),
  locale              varchar(8) NOT NULL DEFAULT 'vi',
  utm                 jsonb,                      -- {source,medium,campaign,referrer}
  ip_hash             varchar(64),                -- daily-rotating HMAC, never raw (§8)
  ip_hash_day         date,                       -- which day's key produced ip_hash
  user_agent          varchar(255),
  is_suspicious       boolean NOT NULL DEFAULT false,
  created_at          timestamptz NOT NULL DEFAULT now(),
  updated_at          timestamptz NOT NULL DEFAULT now()
);

-- One live submission per (form, person, course). A second course is a second row.
CREATE UNIQUE INDEX "UQ_form_submission_live"
  ON form_submission (form_definition_id, email_normalized,
                      COALESCE(selected_course_id, '00000000-0000-0000-0000-000000000000'::uuid))
  WHERE is_latest;

CREATE TABLE form_answer (
  id             uuid PRIMARY KEY DEFAULT uuid_generate_v4(),
  submission_id  uuid NOT NULL REFERENCES form_submission(id) ON DELETE CASCADE,
  question_id    uuid NOT NULL REFERENCES form_question(id),
  text_value     text,        -- free text, and the "Khác" detail of a select question
  number_value   numeric(10,2),
  created_at     timestamptz NOT NULL DEFAULT now(),
  UNIQUE (submission_id, question_id)
);

-- one row per selected option: the reason every chart stays a GROUP BY
CREATE TABLE form_answer_option (
  id                 uuid PRIMARY KEY DEFAULT uuid_generate_v4(),
  answer_id          uuid NOT NULL REFERENCES form_answer(id) ON DELETE CASCADE,
  question_id        uuid NOT NULL REFERENCES form_question(id),   -- denormalised for fast agg
  submission_id      uuid NOT NULL REFERENCES form_submission(id) ON DELETE CASCADE, -- ditto
  option_code        varchar(64) NOT NULL,
  option_group_key   varchar(64),
  UNIQUE (answer_id, option_code)
);

-- C5. Form A carries TWO consents ("I understand this is live group Zoom" and
-- "I agree to be contacted"). One boolean cannot say which one was given.
CREATE TABLE form_submission_consent (
  id            uuid PRIMARY KEY DEFAULT uuid_generate_v4(),
  submission_id uuid NOT NULL REFERENCES form_submission(id) ON DELETE CASCADE,
  consent_code  varchar(64) NOT NULL,   -- matches form_question.consent_code
  version       varchar(16) NOT NULL,   -- FORM_CONSENT_VERSION at the moment of signing
  accepted_at   timestamptz NOT NULL DEFAULT now(),
  UNIQUE (submission_id, consent_code)
);

CREATE TABLE form_submission_event (
  id             uuid PRIMARY KEY DEFAULT uuid_generate_v4(),
  submission_id  uuid NOT NULL REFERENCES form_submission(id) ON DELETE CASCADE,
  event          varchar(32) NOT NULL,   -- created|resubmitted|superseded|status_changed|note_added|assigned|emailed|exported|bot
  from_status    varchar(24),
  to_status      varchar(24),
  actor_user_id  integer REFERENCES "user"(id) ON DELETE SET NULL,
  payload        jsonb,
  created_at     timestamptz NOT NULL DEFAULT now()
);
```

`form_open_text_tag` moves to **V1.1** with the open-text reader that gives it a purpose (§13). Tagging a dozen answers by hand is not worth a table.

**Indexes**

```sql
CREATE UNIQUE INDEX "UQ_master_data_code_group_code" ON master_data_code(group_id, code);
```

**Re-submission (C6, replaces the old update-in-place rule).** When a submission arrives for a `(form_definition_id, email_normalized, selected_course_id)` that already has a live row:

- the previous row keeps its answers, gets `is_latest = false` and `superseded_by_id = <new id>`, and emits a `superseded` event;
- the new row inherits `status`, `assigned_to_user_id` and `internal_notes` so the operator's work is not lost, and emits `resubmitted`;
- if the previous row is `approved` / `rejected` / `archived`, the new row starts at `new` — a rejected applicant may genuinely re-apply.

Nothing is ever overwritten, so "demand for BA in October" stays answerable in December, and a person interested in two courses is two rows rather than one row that ate the other.

## 3. Taxonomy & conditional questions
### 3.1 The join key that makes the supply×demand matrix work

All three forms point their profession question at the **same existing group, `expertise_area`** (D8). Without a shared taxonomy the instructor-supply vs student-demand matrix cannot be computed — the fields simply will not join.

Reusing `expertise_area` rather than minting `career_field` buys something the first draft could not have: **`instructor_expertise` already binds real instructor profiles to those codes**. Supply is therefore "instructors we actually have, plus applicants in the pipeline", not "applications received since this feature shipped" (§6.5).

**Rules**

- Profession codes are frozen before the first production submission. Adding a field later is additive (safe); **renaming or merging is a data migration**.
- `career_interest` (student onboarding: `technology`, `business`, `design`, …) stays where it is. It is a coarser "area of life" list and is **not** merged into `expertise_area`; if the two ever need to meet, that is a mapping table, not a rename.

### 3.2 Per-form option subsets

The same group, three different subsets — which is exactly why `form_question_option` exists (§2.2):

| Form | Question | Offers |
|---|---|---|
| A | "Bạn muốn đăng ký khoá học nào?" | 6 codes — the professions with a course (BA, DA, QA, Supply Chain, PM) + `other` |
| B | "Bạn quan tâm đến nghề/lĩnh vực nào?" | 11 codes, **multi-select**, incl. `undecided` + `other` |
| C | "Lĩnh vực chuyên môn của bạn là gì?" | 11 codes, single-select, + `other` |

Two consequences the first draft missed:

1. **Form B is multi-select.** A person interested in BA *and* Data Analytics is one person with two interests. Demand comes from `form_answer_option` (§6.2); `primary_field_code` stays NULL for this form.
2. **`undecided` is not demand.** It is a real answer and a useful count on its own ("N people want a career but no field yet"), excluded from the demand ranking and the matrix.

### 3.3 Conditional skill group (Form A)

```
Q: profession                  (single_select, group = expertise_area, allowlist = 6 codes)
 ├── skills                     (multi_select, group = form_skill,
 │                               parent_question_id = <profession>,
 │                               parent_option_code = 'business_analysis')
 └── skills_other_text          (long_text, shown for every profession with no seeded list)
```

Seed state per branch:

| parent_option_code | Skill checklist |
|---|---|
| `business_analysis` | 10 codes, from the PDF, verbatim |
| `data_analytics`, `software_testing_qa`, `supply_chain`, `project_management`, `other` | **free-text fallback** until the content exists (D4) |

The fallback is what removes D4 from the critical path: the answers still arrive, they just arrive as text. Turning a branch into checkboxes later is a seed + a question row — the earlier text answers stay readable next to the new counts.

The public definition endpoint returns the whole tree with each conditional question carrying its `parentOptionCode`; the FE renders the matching subset. No extra round trip.

## 4. Public API
| Method | Endpoint | Auth | Notes |
|---|---|---|---|
| `GET` | `/public/forms/:code?courseId=` | none | Localised definition: sections → questions → **allowed options** → conditionals with `parentOptionCode`. Honours `X-Locale` (`vi` default, `en` supported — the existing `locale-context.middleware` already reads that header) and sets `Vary: X-Locale` |
| `GET` | `/forms/:code/prefill?courseId=` | `AuthGuard('jwt')` | Returns `{ fullName, email, phone, currentLevel, professionCode, selectedCourseId }` for the certificate overlay |
| `POST` | `/public/forms/:code/submissions` | none | Creates a submission. Returns `201 { id, status }` |

**Why prefill is its own endpoint.** This application has no global `APP_GUARD` (§1.1): a controller without `@UseGuards` never populates `request.user`, so "include prefill if a JWT happens to be present" would mean writing an optional-auth guard and reasoning about a route that is half-public. A separate authenticated `GET` is smaller, and the FE already knows whether it has a session — it is the certificate screen.

**Request body**

```jsonc
{
  "answers": [
    { "questionCode": "full_name",     "text": "Nguyễn Mai Anh" },
    { "questionCode": "email",         "text": "mai@example.com" },
    { "questionCode": "profession",    "optionCodes": ["business_analysis"] },
    { "questionCode": "skills",        "optionCodes": ["sql", "jira_confluence", "wireframing"] },
    { "questionCode": "session_slot",  "optionCodes": ["weekday_evening", "sat_morning"] },
    { "questionCode": "referral_source", "optionCodes": ["other"], "text": "Thầy giáo giới thiệu" },
    { "questionCode": "biggest_challenge", "text": "…" }
  ],
  "consents":     ["zoom_format", "contact"],   // consent_code list, not a boolean
  "courseId":     "uuid-or-null",
  "context":      { "source": "certificate", "locale": "vi",
                    "utm": { "source": "facebook", "medium": "social", "campaign": "fall_2026" },
                    "referrer": "https://…" },
  "_hp":          "",            // honeypot — must be empty
  "startedAt":    1763000000000  // epoch ms, for the fill-time signal
}
```

**Server-side validation (independent of the client)**

- `questionCode` must belong to this form's active version
- `is_required` questions must be present and non-empty
- **option codes must be in that question's allowlist** (`form_question_option`), not merely somewhere in the group — the group is wider than any single form (§3.2)
- a conditional question is only accepted when its parent answer contains `parent_option_code`
- **`allow_other`**: selecting `other` requires a non-empty `text` on the same answer. This is the only channel through which the taxonomy learns what it is missing, so it is enforced, not optional
- `min_length` **and `max_length`** for text answers (`FORM_LONG_TEXT_MIN_DEFAULT=10`, `FORM_LONG_TEXT_MAX_DEFAULT=2000`) — a public endpoint with an unbounded `text` column is a free storage API
- `email` format + normalisation; `phone` VN format tolerated (not enforced)
- every consent the form declares `is_required` on must appear in `consents`; each one is written to `form_submission_consent` with the current `FORM_CONSENT_VERSION`

**Status codes**: `201` created (also for a re-submission — a new row, §2.3) · `422` validation error (field-mapped) · `429` rate limited (`{ code: "RATE_LIMITED", retryAfterSecs }`, plus `Retry-After`, from the existing guard) · `409` the previous submission is locked by an operator action that forbids replacement.

> The old `200 = dedupe hit` case is gone with update-in-place (C6).

## 6. Analytics — component → query mapping (V1.1 unless marked)
The charts exist to answer five questions. Anything that answers none of them is cut. **Only 6.1 ships in V1** — the rest are written out here so the schema can be checked against them now, and built when there is data to check them against.

Every query below filters `is_latest` (§2.3): superseded rows are history, not current demand.

### 6.1 KPI strip — V1

```sql
SELECT d.code,
       COUNT(*) FILTER (WHERE s.created_at >= now() - interval '7 days') AS last_7d,
       COUNT(*) AS total,
       COUNT(*) FILTER (WHERE s.status = 'new') AS pending
FROM form_submission s
JOIN form_definition d ON d.id = s.form_definition_id
WHERE s.created_at BETWEEN :from AND :to
  AND s.is_latest AND s.status <> 'archived'
GROUP BY d.code;
```

### 6.2 Demand by profession — V1.1

Read from the **options**, not from the denormalised column: Form B is multi-select, so a single column would silently drop two thirds of a person's answer (C4).

```sql
SELECT o.option_code AS field,
       COUNT(*)                          AS n,
       COUNT(DISTINCT s.email_normalized) AS people
FROM form_answer_option o
JOIN form_question   q ON q.id = o.question_id
JOIN form_submission s ON s.id = o.submission_id
JOIN form_definition d ON d.id = s.form_definition_id
WHERE q.code = 'profession'
  AND d.code IN ('advanced_course_interest','free_course_waitlist')
  AND o.option_code NOT IN ('undecided','other')      -- §3.2: real answers, not signals
  AND s.created_at BETWEEN :from AND :to
  AND s.is_latest AND s.status <> 'archived'
GROUP BY 1 ORDER BY n DESC;
```

`people` next to `n` matters: one person submitting three times is **not** three students of demand. Report `undecided` as its own figure beside the ranking, never inside it.

### 6.3 Skill frequency (the strongest content signal) — V1.1

```sql
SELECT q.label_translations ->> :locale AS skill, COUNT(*) AS n
FROM form_answer_option o
JOIN form_question   q ON q.id = o.question_id
JOIN form_submission s ON s.id = o.submission_id
WHERE q.code = 'skills'
  AND (:field IS NULL OR s.primary_field_code = :field)
  AND s.created_at BETWEEN :from AND :to
  AND s.is_latest
GROUP BY 1 ORDER BY n DESC;
```

This is why options are rows, not a joined string: the query is a single `GROUP BY`. For professions still on the free-text fallback (§3.3) there is no ranking — the reader in §6.7 is the whole answer.

### 6.4 When can a class actually run — V1.1

The first draft crossed "which day" with "which hour band" into a heatmap. Those two questions overlap in the source PDF — "Tối Thứ 2–6" already names a time — so the grid contains cells that cannot exist ("Sáng Thứ 7" × "20:00–22:00"), and a single-select forces someone free on both Saturday and Sunday to drop one. D10 merges them into one multi-select slot:

```sql
SELECT o.option_code AS slot, COUNT(DISTINCT s.email_normalized) AS people
FROM form_answer_option o
JOIN form_question   q ON q.id = o.question_id
JOIN form_submission s ON s.id = o.submission_id
WHERE q.code = 'session_slot'
  AND s.created_at BETWEEN :from AND :to
  AND s.is_latest AND s.status IN ('new','reviewing','contacted','grouped')
GROUP BY 1 ORDER BY people DESC;
```

One ranked bar, read directly as **"which slot has enough people to open a class"** — and because it is multi-select, the counts overlap honestly: 12 people free Saturday morning and 9 of them also free Sunday is a schedulable fact, not a contradiction. Cross it with `primary_field_code` for "BA class, Saturday morning".

### 6.5 Supply × demand matrix — the highest-value visual — V1.1

Supply counts **the instructors this platform actually has** (`instructor_expertise`, already populated) plus the applicants in the pipeline — the change D8 was made for. Counting only Form C would report "no supply" for fields staffed by the instructors already teaching.

```sql
WITH demand AS (
  SELECT o.option_code AS field, COUNT(DISTINCT s.email_normalized) AS n
  FROM form_answer_option o
  JOIN form_question   q ON q.id = o.question_id
  JOIN form_submission s ON s.id = o.submission_id
  JOIN form_definition d ON d.id = s.form_definition_id
  WHERE q.code = 'profession'
    AND d.code IN ('advanced_course_interest','free_course_waitlist')
    AND o.option_code NOT IN ('undecided','other')
    AND s.is_latest AND s.status <> 'archived'
  GROUP BY 1
), supply_existing AS (
  SELECT c.code AS field, COUNT(DISTINCT ie.instructor_id) AS n
  FROM instructor_expertise ie
  JOIN master_data_code c ON c.id = ie.expertise_code_id
  GROUP BY 1
), supply_pipeline AS (
  SELECT s.primary_field_code AS field, COUNT(DISTINCT s.email_normalized) AS n
  FROM form_submission s
  JOIN form_definition d ON d.id = s.form_definition_id
  WHERE d.code = 'instructor_application'
    AND s.is_latest AND s.status IN ('new','reviewing','contacted','approved')
  GROUP BY 1
)
SELECT f.field,
       COALESCE(d.n, 0)  AS demand,
       COALESCE(se.n, 0) AS instructors,
       COALESCE(sp.n, 0) AS applicants
FROM (SELECT field FROM demand
      UNION SELECT field FROM supply_existing
      UNION SELECT field FROM supply_pipeline) f
LEFT JOIN demand          d  ON d.field  = f.field
LEFT JOIN supply_existing se ON se.field = f.field
LEFT JOIN supply_pipeline sp ON sp.field = f.field;
```

Quadrant is classified in the service, not in SQL, on `instructors + applicants`:

| | supply low | supply healthy |
|---|---|---|
| **demand high** | 🔴 **Build instructors first** — do not open a class | 🟢 **Open now** |
| **demand low** | ⚪ De-prioritise | 🟡 Nurture demand |

Both axes count **distinct people**, not submissions — one strong instructor is worth more than three duplicate forms. Thresholds (`demandHigh` = p75, `supplyLow` = 2) are env-configurable: `FORM_MATRIX_DEMAND_P75`, `FORM_MATRIX_SUPPLY_MIN=2`.

```sql
WHERE d.code = 'instructor_application' AND s.is_latest AND s.status <> 'archived'

```

## 7. Frontend plan
### 7.1 Shared architecture (one renderer, three surfaces)

All three forms are **rendered from the API definition**, not hand-coded question by question. One set of field renderers serves every surface:

| Renderer | `question_type` | Options |
|---|---|---|
| `<TextFieldRenderer>` | `short_text` | — |
| `<TextAreaRenderer>` | `long_text` | — |
| `<EmailFieldRenderer>` | `email` | — |
| `<PhoneFieldRenderer>` | `phone` | — |
| `<UrlFieldRenderer>` | `url` | — |
| `<ChipSingleRenderer>` | `single_select` | ✅ from the definition's allowlist |
| `<ChipMultiRenderer>` | `multi_select` | ✅ from the definition's allowlist |
| `<ConsentRenderer>` | `consent` | one per `consent_code` |

**Why data-driven and not hard-coded:** adding a question, reordering a section, or adding a new profession's skill list becomes a **database row, not a deploy**. The cost is roughly +2 FE days; the payoff is that the forms stop being a code-change bottleneck for a content-owned surface. The `form_question_option` allowlist (§2.2) is what keeps that promise — without it the FE would have to know that Form A shows six professions and Form B eleven, and the renderer would be data-driven in name only.

**"Khác" is part of the renderer, not a special case.** A question with `allow_other` renders a text box that becomes required the moment `other` is selected, mirroring the server rule (§4).

**Conditional rendering** — a question renders only when its parent's current selection includes `parentOptionCode`:

```ts
const visible = (q, values) =>
  !q.parentOptionCode ||
  (values[q.parentQuestionCode] ?? []).includes(q.parentOptionCode);
```

**State**

| Concern | Choice | Why |
|---|---|---|
| Field state + validation | React Hook Form + **`yupResolver`** | The client ships `yup` 1.7 and `@hookform/resolvers`, and every existing form (sign-up, instructor profile) is built this way — there is no `zod` in the dependency tree. The schema is built dynamically from the definition, including `min_length` / `max_length` |
| Draft persistence | Zustand `useFormDraftStore` → `sessionStorage` | A 15-question wizard must survive an accidental reload; scoped per `formCode` |
| Server data | React Query (or existing fetcher) | Definition cached per `formCode` + locale |

**i18n** — question labels, placeholders and options arrive **already localised** from the API via `X-Locale` (EPIC-06 pattern; the header is already read by the API's locale middleware). Only UI chrome (button text, error messages) goes through the FE translation layer. This avoids duplicating the entire question bank in FE translation files.

**Accessibility floor**

- one `<fieldset>` + `<legend>` per `section_code`
- errors wired via `aria-describedby`, announced with `aria-live="polite"`
- failed step → focus moves to the **first invalid field** (not the top of the form)
- chips are real `<button type="button">` with `aria-pressed`; never clickable `<div>`s
- overlay traps focus and restores it to the trigger on close
- respects `prefers-reduced-motion`

## 8. Anti-spam & rate limiting
A public form on a marketing page **will** be hit by bots. Layered defences, cheapest first — and **built on the limiter this project already has** (`RateLimitGuard`, `@RateLimit(limit, windowMs, by)`, §1.1) rather than a second, parallel set of `FORM_RATE_LIMIT_*` knobs.

```ts
@UseGuards(RateLimitGuard)
@RateLimit(3,  HOUR,          { body: 'email' })   // the key that actually identifies a person
@RateLimit(20, HOUR,          'ip')                // a coarse net, not the real defence
@Post(':code/submissions')
```

| Layer | Rule | Why this number |
|---|---|---|
| Honeypot | `_hp` must be empty. If filled → store with `status='archived'`, `is_suspicious=true`, emit a `bot` event, return `201` so the bot believes it worked | always on |
| Fill time | `now - startedAt < FORM_MIN_FILL_MS` (2000) → **accept and flag `is_suspicious`**, never reject | The first draft returned `422`. Form B is five fields with prefill; a fast human clears it in under three seconds, and a rejected real signup on a landing page costs more than a junk row costs |
| Rate limit (email) | 3 / hour per normalised email | The real key. A bot rotating IPs still has to rotate mailboxes |
| Rate limit (IP) | **20 / hour** | The draft's 5/hour blocks a classroom, an office or a café on one NAT — exactly the rooms where this form gets demoed. Widen per deployment with the existing `RATE_LIMIT_IP_MULTIPLIER` |
| ⚠️ Counter scope | in-process `Map` (§1.1) | Behind N replicas the effective budget is N×. Acceptable for an abuse guard; a hard quota would need a shared store |
| Captcha | off by default; pluggable | `FORM_CAPTCHA_PROVIDER=none\|hcaptcha\|recaptcha_v3`, `FORM_CAPTCHA_SECRET` — turn on only if the flags above are actually losing |
| Re-submission | append-only, live row per (form, email, course) (§2.3) | Replaces the 30-day update-in-place window |
| IP storage | `hmac_sha256(key = FORM_IP_HMAC_SECRET ‖ date, ip)`, `ip_hash_day` stored alongside, **deleted after 30 days** | `sha256(ip + salt)` is **not** anonymisation: the whole IPv4 space is 2³² values, so a leaked table plus the salt is reversed by brute force in minutes. A key that changes daily means yesterday's hashes can no longer be linked or reversed, while same-day abuse detection still works |
| Double opt-in | waitlist only — the address joins the notification list only after clicking a confirm link | V1.1 |

Body size is capped by `max_length` validation (§4), so a public `text` column cannot be used as free storage.

## 9. Consent, retention & compliance
**Never infer consent, and never collapse two consents into one.** Form A asks for two distinct things, and the PDF words them separately:

| `consent_code` | Text (PDF, Form A) | Nature |
|---|---|---|
| `zoom_format` | "Tôi hiểu đây là chương trình **học trực tiếp qua Zoom theo nhóm** và có hoạt động thực hành ngoài giờ học." | Acknowledgement of what the product is |
| `contact` | "Tôi đồng ý để [DNA Academy] liên hệ nhằm **tư vấn khoá học, xếp nhóm và xác nhận lịch học**." | Consent to be contacted about personal data |

Each accepted consent writes one `form_submission_consent` row — `consent_code`, `version` (`FORM_CONSENT_VERSION=v1`), `accepted_at`. Bumping the wording bumps the version, so it stays provable **which text** a person agreed to and **which of the two** they gave. A single `consent_given` boolean cannot answer either question, which is the whole point of keeping the record.

**Forms B and C have no consent line in the source PDF** (D9). Both collect an email address and C collects a phone number, so V1 adds one `contact` consent to each; if legal decides otherwise, AC-08 must be narrowed to Form A.

Vietnam's personal-data-protection framework requires **clear, voluntary consent before processing** personal data and grants data subjects rights to **access, correct and delete** their data (Decree 13/2023/ND-CP; the framework has since been revised — a replacement instrument was announced in 2026, so **confirm the currently effective text with legal before launch**). Sources: [DLA Piper — Data protection laws in Vietnam](https://www.dlapiperdataprotection.com/?t=law&c=VN), [Securiti — Vietnam's Personal Data Protection Decree](https://securiti.ai/vietnam-personal-data-protection-decree/).

| Requirement | Implementation |
|---|---|
| Purpose limitation | Consent copy states the purpose: course consultation, cohort scheduling, launch notifications |
| Right of access / correction | Admin can export or amend any submission |
| Right of erasure | `POST /public/forms/erasure-request` (email-verified) → queues deletion of **every** row for that `email_normalized`, including superseded ones; admin can also delete from the detail drawer |
| Retention | `FORM_RETENTION_MONTHS=24`; scheduled job soft-archives, then hard-deletes after the window, writing an event each time. Superseded rows follow the live row's clock |
| IP data | `ip_hash` is a daily-rotating HMAC and is cleared after 30 days (§8) — it is an abuse signal, not a record |
| Data minimisation | V1 collects no ID numbers, no health, no financial data. **If a CV/file upload is added to Form C later, re-assess and get legal sign-off first** |
| Sensitive fields | Phone number is the most sensitive field collected — required only on Form A, optional on B and C |
| Transparency | Link to the privacy policy sits next to every consent checkbox |

⛔ **Gate**: legal review of consent wording + retention policy is a **launch blocker**, not a follow-up.

## 12. Acceptance criteria
**Public forms**

- **AC-01** The definition endpoint returns all three forms with sections, questions, **the allowed option subset per question** and conditionals, in `vi` and `en`; `Vary: X-Locale` is set.
- **AC-02** Choosing a profession on Form A renders that profession's skill checklist **without a network round trip**; switching profession swaps the list; a profession with no seeded list renders the free-text fallback (§3.3).
- **AC-03** A required question left empty is rejected **server-side** with a field-mapped `422`, regardless of client state.
- **AC-04** Form C cannot advance past an invalid step, and on failure focus lands on the first invalid field.
- **AC-05** Reloading mid-wizard restores the draft (sessionStorage) for the same `formCode`.
- **AC-06** Successful submission shows the in-place success state; no page navigation; a second click cannot double-submit.
- **AC-07** On `STU_CER_10`, the bottom row shows exactly `Về trang chủ` + `Đăng ký khoá học chuyên sâu`; the overlay opens pre-filled with name, email, phone and `current_level = dna_intro_completed`.
- **AC-08** Every consent a form declares required is stored as its own `form_submission_consent` row with `consent_code`, `version` and `accepted_at`; **Form A stores two rows**; a submission missing a required consent is rejected `422`.
- **AC-09** Honeypot-tripped submissions are stored `archived` + `is_suspicious` and never appear in default admin lists. A submission filled in under `FORM_MIN_FILL_MS` is **accepted and flagged**, not rejected.
- **AC-10** A second submission for the same email **and the same course** creates a new row, flips the previous one to `is_latest = false` with `superseded_by_id` set, carries over status/assignee/notes, and emits `resubmitted` + `superseded`. The earlier answers remain readable. Two different courses give two live rows, neither one overwriting the other.
- **AC-11** An option code that exists in the group but is **not** in that question's allowlist is rejected `422`.
- **AC-12** Selecting `other` without accompanying text is rejected `422`; the text is stored on the same answer row.
- **AC-13** A text answer longer than `max_length` is rejected `422`.

**Admin**

- **AC-14** The submissions list filters by form, status, field, course and date range, defaults to live rows only, and the filter state survives a page reload (URL-synced).
- **AC-15** Changing status writes an event row; the detail drawer renders the full timeline in order, and the superseded chain is reachable from it.
- **AC-16** Form C question 11 is visible without expanding anything on the applicant detail view.
- **AC-17** CSV export honours the current filters and exports one row per submission with options flattened.
- **AC-18** An account without `forms:view` gets `403` on every `/admin/forms/*` route, and the seeding migration grants all four `forms:*` permissions to Admin.

**V1.1 analytics** (verify when built)

- **AC-19** Demand counts a Form B respondent who picked three professions once **in each** of the three, and excludes `undecided` from the ranking while reporting it separately.
- **AC-20** The supply×demand matrix uses **distinct people** on both axes, counts existing instructors from `instructor_expertise` as supply, and visibly flags one high-demand / low-supply field as the priority quadrant.
- **AC-21** Slot ranking matches a manual count of the underlying option rows, including people who chose several slots.
- **AC-22** Skill frequency for one profession matches a manual count of the raw answers.

**Non-functional**

- **AC-23** Both landing forms are keyboard-operable end to end; chips are buttons with `aria-pressed`.
- **AC-24** p95 of every analytics endpoint < 400 ms at 5,000 submissions on the staging dataset.
- **AC-25** No raw IP address is persisted anywhere in the forms tables, `ip_hash` is a daily-rotating HMAC, and rows older than 30 days have it cleared.
